- (insight) the data-model question and the stack question are the SAME question. If FR-1's assertion is a row, plain relational tables model it directly; a graph store fights it, because a disputed/superseded/retracted assertion is not naturally an edge, and FR-48's merge becomes destructive unless merge is itself modelled as an assertion.
- (decision by user) a person IS a real row with a stable identity — NOT an identity that emerges from a cluster of assertions. Duplicates are detected after the fact and resolved by merging. Chosen for implementation simplicity at this scale.
- (consequence) the person row therefore holds the currently-accepted values and acts as a projection; the assertion table holds every claim about that person with its source and confidence tier, including the claims that lost. FR-1 is satisfied by the assertion table, not by dissolving the person row.
- (question, open) FR-48 explicitly requires that a wrong merge can be undone. That requirement — not the merge itself — decides the mechanism: a destructive merge makes un-merge expensive, a link-based merge makes it nearly free. This is the one call the person-as-row decision does not settle.
- (decision by user) merge mechanism A — destructive merge with a tombstone: the losing person row becomes a tombstone redirecting to the winner, and every reference is repointed. Link-based merge (B) was laid out with its cheaper un-merge and was not chosen.
- (constraint, follows from A) because FR-48 still requires un-merge, the merge must execute as ONE logged, reversible transaction that records every reference it repointed. Without that record un-merge is not expensive but impossible, and FR-48 breaks. This is the price of choosing A and it is non-negotiable.
- (decision by user) on a conflicting value, the losing value is discarded rather than retained as a competing assertion — approver picks one, the other does not survive as live data.
- (constraint, follows) "discarded" must mean discarded as a live assertion, NOT deleted outright: FR-39 requires the revision log to record what changed from which value to which, and to reconstruct the tree at a past instant. The losing birth year therefore dies in the assertion table and survives in the revision log. Implementing it as a hard delete would break FR-39.

- (decision by user) all data access goes through ONE path — no route handler or Server Action may reach the database directly. This is the paradigm call: a domain core owns every read and write, and the Next.js layer is an adapter that can only reach data through the core's exposed operations.
- (consequence) the four cross-cutting invariants that must never be re-implemented per route — privacy radius (FR-37), clan partitioning (NFR), revision logging (FR-39), two-tier write routing (FR-3) — live in the core and are enforced structurally rather than by developer memory. A new route cannot forget them because it has no way to bypass them.

On serverless it would have needed either transaction-wrapping every query or abandoning RLS for application-layer filtering — the VPS choice removes that whole class of subtlety.

- (decision by user) duplicates are NOT prevented at write time. Ambiguous input creates a second person row; both coexist; a detector sweeps for candidate duplicates and reports them for a human to judge. Nothing merges automatically.
